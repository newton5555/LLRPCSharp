02 / SDK STATE & RESOURCE MODEL

设备现实与托管意图：解耦与双轨管理

在工业 RFID 环境中，多个客户端或手工指令可能随时改写读写器配置。LLRPCSharp 状态模型的核心是将“应用期望的配置意图 (DesiredState)”与“设备当前的实际状态快照 (ObservedState)”彻底解耦，保障在任意底层改动后托管层依然能够准确观测与恢复。

两种状态维度的分离

DESIRED STATE (期望意图)

应用想要什么

由 ApplySettingsAsync 或 StartInventoryAsync(settings) 设置并持久保存在客户端内存中。底层的 Raw 或专家操作绝不会清除它。

reader.DesiredSettings
OBSERVED STATE (设备事实)

设备当前是什么

由连接查询、主动事件和资源刷新操作更新。状态可能是 Unknown、Stale 或 Synchronized。

reader.ObservedState

典型状态转换流程

01

托管盘点正常运行

DesiredState = Settings A，设备上存在由 SDK 部署的 ROSpec 14150，ObservedState = Synchronized。

02

底层 Raw / 专家修改

外部系统或 reader.Protocol 发送了 DELETE_ROSPEC。设备端资源发生改变，ObservedState 变为 Stale，但 DesiredState 依然保持 Settings A。

03

状态观测刷新

调用 reader.SynchronizeStateAsync() 重新查询设备事实快照。快照确认 14150 已丢失，但不会自动重新下发。

04

托管重新收敛

调用无参 reader.StartInventoryAsync()，SDK 根据保留的 DesiredState 重新编译并下发 ROSpec 14150，恢复托管盘点并将 ObservedState 置回 Synchronized。

SynchronizeStateAsync 到底做什么

SynchronizeStateAsync() 是一个纯观察操作，它不是使用托管 API 的强制前置条件。

它保证：
  • 向设备查询并刷新 GET_ROSPECS 与 GET_ACCESSSPECS 快照
  • 准确识别 Foreign（其他应用创建）与 Managed 资源
  • 将 reader.ObservedState 置为 Synchronized
它不保证：
  • 不会自动改写或删除设备上的任何资源
  • 无法防止其他第三方客户端在查询瞬间之后再次改写设备
  • 无法自动解析未经扩展注册的私有厂商参数

恢复与重建规则

当底层操作删除了 SDK 资源，或者网络重连导致设备重置后，可直接调用无参启动恢复： 

// 模拟底层 Raw 操作删除了 ROSpec
await reader.Protocol.TransactAsync<V101Messages.DELETE_ROSPEC_RESPONSE>(
    new V101Messages.DELETE_ROSPEC(reader.Protocol.NextMessageId()) { ROSpecID = 14150 });

// 此时 reader.ObservedState 为 Stale，但 reader.DesiredSettings 完好
// 高层一键根据 Desired 重新部署并恢复运行
await using InventorySession session = await reader.StartInventoryAsync();
注意：如果底层操作创建的是专有业务 ROSpec，应使用 StartExistingRoSpecAsync(roSpecId) 桥接运行，避免使用托管配置覆盖它。
