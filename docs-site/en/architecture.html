04 / SYSTEM ARCHITECTURE

A focused business facade over an open protocol core

LLRPCSharp separates byte transport, LLRP framing, generated versioned models, state management and managed reader APIs. The same foundation also supports offline decoding, automation and deterministic software devices.

From LTK.NET to LlrpNet

LTK.NET established the useful pattern of generating strong protocol types from machine-readable definitions. LlrpNet keeps that definition-driven approach and updates the surrounding design for modern .NET. The comparison below describes design choices, not unbenchmarked performance guarantees.

DimensionLegacy LTK.NETLLRPCSharp / LlrpNet
DefinitionsSingle XML input and legacy transforms.Official XML plus YAML-driven generation into typed immutable models and codecs.
MemoryOlder collection and byte-array patterns.ReadOnlyMemory<byte>, Span<byte> and BinaryPrimitives are used where appropriate to avoid unnecessary copies.
ConcurrencyAPM or blocking patterns.async/await, channels, async streams and bounded report flow.
VersioningPrimarily fixed around one protocol model.Independent 1.0.1, 1.1 and 2.0 namespaces with explicit adapters.
Managed APICallers build deeply nested parameter trees.ReaderSettings, InventorySession and Tag Access express common intent.
Migration note: Existing applications still need verification against their messages, target readers and negotiated versions. This page does not promise a universal compatibility percentage or fixed throughput multiplier.

Resource ownership and isolation

The managed facade uses reserved resource IDs while preserving a boundary for resources owned by other applications.

MANAGED

SDK-owned resources

ROSpec 14150 and AccessSpec 14151 are managed and converged by the high-level API.

FOREIGN

Foreign resources

PreserveForeign keeps resources created elsewhere and reports conflicts instead of silently deleting them.

BRIDGED

Existing ROSpec

StartExistingRoSpecAsync(id) can feed an existing resource into the managed report pipeline without redefining it.

Protocol adapter boundary

Each supported protocol version has its own generated namespace. High-level code must not hide the version behind a default alias; adapters own the cross-version translation.

using V101Parameters = LlrpNet.Protocol.Parameters.V1_0_1;
using V11Parameters = LlrpNet.Protocol.Parameters.V1_1;
using V20Parameters = LlrpNet.Protocol.Parameters.V2_0;

V101Parameters.ROSpec roSpec101 = new(roSpecID: 14150, priority: 0, ...);
V11Parameters.ROSpec roSpec11 = new(roSpecID: 14150, priority: 0, ...);

Server and virtual device

The repository includes a deterministic software LLRP reader for CI and application integration. It covers protocol, lifecycle and business-flow behavior; it is not an RF waveform or physical-environment simulator.

  • LlrpDevice.Abstractions defines device contracts and execution state.
  • LlrpDevice.Server provides the device-side TCP server and resource routing.
  • LlrpDevice.Virtual provides repeatable tags, antenna filtering, RSSI jitter and C1G2 memory behavior.
  • LlrpDevice.Virtual.Hosting exposes an embeddable host.
  • LlrpVirtualDevice.Cli provides presets and lifecycle commands.
Interop note: Standard and Impinj-shaped software profiles are useful for connection and inventory tests. Advanced vendor behavior still requires a target-specific test.

Definitions and code generation

Protocol entities originate in definitions/ and are generated into messages, parameters, enumerations and codecs. Generated *.g.cs files are committed artifacts and must not be hand-edited; change the definition, importer or generator and regenerate instead.
