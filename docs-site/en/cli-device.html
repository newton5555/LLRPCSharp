LLRPCSHARP / CLI USER’S GUIDE

Virtual Device CLI User’s Guide

LlrpVirtualDevice.Cli is the device-side command-line tool. One process hosts one deterministic virtual LLRP device and exposes a normal TCP endpoint so the Reader SDK, WPF clients or third-party LLRP clients can be tested without physical hardware.

1. Scope and launch

Run it from the source tree. With no arguments it enters the interactive device shell but does not create a device:

dotnet run --project src/LlrpVirtualDevice.Cli/LlrpVirtualDevice.Cli.csproj

The executable name used by the built-in help is llrp-virtual-device; source runs use the project path above.

This is a one-device tool, not a multi-device manager. It does not restore ROSpec, AccessSpec or inventory state after a process restart.

2. Run modes

llrp-virtual-deviceEnter the shell without creating a device.
llrp-virtual-device run [options]Create and run one device in the foreground; Ctrl+C stops it.
llrp-virtual-device live [options]Create and start one device, then enter the shell with RX/TX events enabled.
llrp-virtual-device shellExplicit alias for the empty interactive shell.
llrp-virtual-device validate --config PATHValidate one local JSON device configuration.
llrp-virtual-device presetsList built-in device presets.
llrp-virtual-device capsList capability profiles.
# Quiet foreground service
dotnet run --project src/LlrpVirtualDevice.Cli/LlrpVirtualDevice.Cli.csproj -- run --port 5084

# Start and observe RX/TX traffic generated by a client
dotnet run --project src/LlrpVirtualDevice.Cli/LlrpVirtualDevice.Cli.csproj -- live --llrp 1.0.1

live does not manufacture client requests. LlrpCli, the Reader SDK or another LLRP client must connect and drive traffic.

3. Interactive lifecycle shell

Inside the shell, manage the lifecycle as “create → start → observe → stop/destroy”:

vdev (empty)> server create --llrp 1.0.1
vdev (created)> server start
vdev (running)> server status
vdev (running)> logs on
vdev (running)> server stop
vdev (stopped)> server destroy
vdev (empty)> exit
server create [options]Create a host without binding TCP by default.
server run [options]Create and start one device.
server start|stop|restartControl the listener and sessions on the same host.
server statusShow state, endpoint, protocol, profile and client count.
server destroyDispose the current device before creating another.
logs on|off|statusControl lifecycle, client and decoded RX/TX event output.

The default endpoint is 127.0.0.1:5084 with one client slot. Override it with --listen, --port and --max-client-connections.

4. Presets and JSON configuration

The built-in presets describe protocol and device shapes rather than invented business scenarios:

llrp.standard101.basic

LLRP 1.0.1 standard device with deterministic tag reports.

llrp.standard101.strict

LLRP 1.0.1 standard device with strict inventory state checks.

llrp.standard11.basic

LLRP 1.1 device with explicit version negotiation.

llrp.standard20.basic

Current translated LLRP 2.0 device baseline.

impinj.r420.basic

Impinj R420-shaped LLRP 1.0.1 extension device.

The configuration selects a capability profile, data source, report cadence and deterministic RF-observable behavior. The listen address, port and runtime ROSpec/AccessSpec state are not stored:

{
  "schemaVersion": 1,
  "presetId": "llrp.standard101.basic",
  "capabilityProfileId": "llrp1.0.1_standard",
  "protocolVersion": "1.0.1",
  "inventoryDataSource": "default",
  "reportIntervalMilliseconds": 100,
  "repeat": true,
  "rfScenario": "static",
  "randomSeed": 2026,
  "singleTagProbability": 0.85,
  "maxTagsPerRound": 2,
  "tags": [
    {
      "epc": "E28011910000000000000001",
      "antennaId": 1,
      "peakRssi": -55,
      "tid": "E280110520007001",
      "userMemory": [4660, 22136]
    }
  ]
}
# Validate
dotnet run --project src/LlrpVirtualDevice.Cli/LlrpVirtualDevice.Cli.csproj -- validate --config virtual-device.json

# Run the configuration
dotnet run --project src/LlrpVirtualDevice.Cli/LlrpVirtualDevice.Cli.csproj -- run --config virtual-device.json

The standard profile exposes four logical antennas and a deterministic inventory source. static, moving-tags and noisy control observable tag behavior; they are not physical RF waveform simulation.

5. Client interoperability

After startup, any ordinary LLRP client can connect to 127.0.0.1:5084. A typical workflow is:

01Start the device with llrp-virtual-device run or live.
02Connect with LlrpCli, LlrpSdk or another LLRP client.
03Use logs on to observe capability, ROSpec and report RX/TX events.

The Impinj R420 profile has been checked with ItemTest 2.10.0 for the LLRP 1.0.1 connection and inventory-start path. This is an LLRP-path compatibility statement, not an implementation claim for mDNS, rshell/SSH or other non-LLRP services.

6. Tool boundaries

Virtual Device CLI is an SDK testing tool, not a primary product API presented on the home page. If you need to embed a virtual device in xUnit or WPF, use the Virtual Device API Reference; for command-line interoperability, stay in this guide.
  • Covers device-side connection, capabilities/configuration, ROSpec/AccessSpec lifecycle, reports and standard Tag Access paths.
  • Does not drive a physical RFID module or calculate Tx power, sensitivity, Tari, distance or collision physics.
  • Hosts one device by design; there is no multi-device directory or cross-process recovery.
  • Protocol-version and vendor-profile behavior remains bounded by current status and interoperability evidence.
